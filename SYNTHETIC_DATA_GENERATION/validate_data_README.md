# AnomX — Synthetic Data Validation

## Overview

`validate_data.py` validates the synthetic financial-event dataset generated by `generate_events.py`.

It performs structural, label, timestamp, and numerical checks to identify data-quality issues before exploratory data analysis (EDA) and machine-learning model development.

The script reads the generated CSV, prints a validation summary, and saves reports without modifying the original dataset.

## Requirements

- Python 3.13 or a compatible Python version
- pandas
- PyYAML
- The AnomX synthetic dataset generated by `generate_events.py`
- The project configuration file at `configs/config.yaml`

Install missing dependencies inside the project's virtual environment:

```powershell
python -m pip install pandas pyyaml
```

## How to Run

Run these commands from the AnomX project root.

### 1. Generate the dataset

```powershell
python .\SYNTHETIC_DATA_GENERATION\generate_events.py
```

### 2. Validate the dataset

```powershell
python .\SYNTHETIC_DATA_GENERATION\validate_data.py
```

The script reads the CSV path configured through `data.raw_path` in `configs/config.yaml`. If that setting is absent, it defaults to `data/raw/events.csv`.

## Validation Checks

### 1. Data Integrity

Checks that:

- The dataset is not empty.
- Column names are present and unique.
- Required columns exist.
- Event IDs are present and unique.
- Missing values are reported.

Missing values are reported as warnings because some event fields may legitimately be empty for particular event types.

### 2. Anomaly Labels

Checks that:

- `is_anomalous` contains only `0` and `1`, with no missing or invalid values.
- Both normal and anomalous events exist.
- `user_is_anomalous`, when available, contains valid binary values.

The distinction between user-level and event-level anomalies is important: an anomalous user can generate ordinary events that should not automatically be labelled anomalous.

### 3. Timestamps

Checks that:

- Timestamps can be parsed.
- Events are chronologically ordered.
- Timestamps fall within the configured date range when both dates are available.

### 4. Numerical Values

For the following columns, when present:

- `deposit_amount`
- `withdrawal_amount`
- `trade_volume`

The script checks for non-numeric values and negative amounts.

These are basic checks; additional business rules may be needed to determine whether each transaction is realistic.

### 5. Anomaly Types and Labels

Reports the distribution of event and anomaly types and cross-tabulates anomaly types against `is_anomalous`.

When `anomaly_type` exists, the script also flags events that have a non-normal anomaly type but a normal event label.

This is a consistency check, not proof that the simulated behaviour is realistic.

### 6. Configured Dataset Size

Compares the actual number of rows against `data.n_events` in the configuration file.

## Generated Reports

The script creates the `reports/` directory if it does not exist.

| File | Purpose |
|---|---|
| `reports/data_validation_report.txt` | Human-readable validation results |
| `reports/data_validation_report.json` | Structured results for programmatic use |

The terminal output also includes:

- Number of rows and columns
- Number of passed checks
- Number of failed checks
- Number of warnings
- Failed-check details, when applicable

## Understanding the Results

Each check has one of three statuses:

| Status | Meaning |
|---|---|
| `PASS` | The check's condition was satisfied. |
| `FAIL` | A required validation condition was not satisfied. |
| `WARNING` | A potential issue needs investigation, but it is not treated as a hard failure. |

A successful run does not guarantee that the dataset is suitable for model training. It means only that the implemented checks did not identify certain classes of problems.

## Current Limitations

The current validation script does not fully verify:

- Whether each anomaly generator produces its intended behavioural pattern.
- Whether anomalous events are sufficiently realistic or diverse.
- Whether `anomaly_fraction` matches the desired event-level anomaly percentage.
- Whether correlated or coordinated accounts behave realistically.
- Whether synthetic data contains unintended leakage that could make model evaluation misleading.
- Whether the dataset is statistically representative of real financial activity.

These require deeper behavioural testing, exploratory data analysis, and eventually model evaluation.

## Recommended Workflow

1. Generate synthetic events using `generate_events.py`.
2. Run `validate_data.py`.
3. Investigate all failures and warnings.
4. Perform exploratory data analysis.
5. Engineer features for anomaly detection.
6. Train baseline models.
7. Evaluate using precision, recall, F1-score, and PR-AUC, alongside other suitable metrics.

## Notes

- Run commands from the project root so that paths resolve correctly.
- The validation script does not modify the source CSV.
- Validation results depend on the checks implemented in the script and should not be interpreted as a certification of data quality.
